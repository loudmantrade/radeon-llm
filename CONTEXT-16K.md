# Тест 16k и повторного использования префикса

Рабочая конфигурация 8k сохранена. Тест не меняет установленный plist, модель, OpenCode-конфиг или штатные настройки сервера.

## Уже проверено на 8k

На рабочем Radeon API выполнены три запроса с документом 1011 токенов и тремя контрольными строками в начале, середине и конце. Все ответы верны.

| Запрос | Из кэша | Пересчитано | Prefill | Полное время |
|---|---:|---:|---:|---:|
| Первый | 1 | 1068 | 17,50 с | 24,93 с |
| Точный повтор | 1068 | 1 | 0,09 с | 3,62 с |
| Тот же документ, новый вопрос | 1060 | 11 | 1,20 с | 4,73 с |

Это единичные измерения на свободном слоте, не прогноз скорости всех задач. Документ не передавался в готовом виде: сервер сохранил KV-префикс и использовал его повторно. Точные данные: `logs/prefix-cache-8k-check.json`.

## Запуск 16k

Сначала закрой OpenCode или оставь его без активного запроса. В обычном macOS Terminal:

```bash
/path/to/radeon-llm/test-16k.command
```

Скрипт временно остановит штатный API 8080 и запустит отдельный процесс на 18082 с:

- Контекстом 16384, одним слотом.
- K и V в Q8_0, Flash Attention on.
- 37 слоями на GPU, без автоматического уменьшения контекста или GPU offload.
- Отключённым RAM-кэшем снимков для изолированного сравнения; активный KV-префикс сохраняется.
- Теми же весами и MoltenVK 1.4.2.

В текущей версии квантованный V-кэш требует Flash Attention. Приблизительная оценка: KV 1224 МиБ плюс веса 2376 МиБ и вычислительные буферы. Фактическое выделение и совместимость проверяются запуском.

Проверяются реальный размер контекста, арифметика, извлечение трёх контрольных строк из документа примерно на 10 тысяч токенов, повторный запрос и общий префикс с новым вопросом. JSON-схема задаёт только структуру ответа, а не ожидаемые значения контрольных строк. Затем выполняется полный API-тест с потоковым вызовом функции.

При успехе, ошибке или Ctrl+C скрипт останавливает свой тестовый процесс и пытается вернуть штатный сервер 8k. После успешного теста 16k автоматически не становится рабочей конфигурацией: сначала нужно оценить журнал и качество. При отключении питания/принудительном kill восстановление нужно выполнить вручную через `daemon.command start`.

Длинный первый запрос может занять несколько минут. Первый prefill включает обработку документа; повторный должен обработать только последний токен или изменившийся хвост.

## Результаты

- `logs/context16k-server.log`: загрузка и ошибки Vulkan, размер KV.
- `logs/context16k-benchmark.json`: ответы, фактическое использование кэша и времена.
- `logs/api-check-18082.json`: полный API-тест, если предыдущие проверки прошли.

Если скрипт завершился ошибкой, пришли консольный вывод и последние строки server log. Статус рабочего сервера:

```bash
cd /path/to/radeon-llm
./daemon.command status
```

Пока выполнены dry-run и синтаксические проверки экспериментального launcher, а логика benchmark реально проверена на существующем сервере 8k. Сам 16k/Q8/FA GPU-запуск ещё не выполнен: из Codex графические устройства недоступны.

## Результат запуска из Terminal

16k/Q8 запустился: 37/37 слоёв весов на GPU, KV 1224 МиБ. Все три контрольные строки из документа на 9996 токенов извлечены верно. Повтор использовал 10053 токена кэша и пересчитал один; новый вопрос использовал 10045 и пересчитал 11. Проверки API прошли, штатный сервер 8k восстановлен.

Первый запрос: 1140,88 с, повтор: 21,93 с, новый хвост: 25,49 с. Генерация при истории около 10k: примерно 1,8 токена/с. Ускорение всего повторного запроса около 52x; число 1988x относится только к prefill.

Причина низкой скорости локализована: Apple/AMD ветка ggml-vulkan.cpp принудительно отключает subgroup_shuffle. GPU Flash Attention без coopmat2 требует shuffle и vote и отклоняется, поэтому внимание выполняется через CPU. Граф содержит 74 части вместо прежних двух. Размещение всех слоёв весов на GPU не означает, что все операции выполняются там.

Этот тест подтверждает корректность 16k и эффективность KV-префикса, но конфигурация слишком медленная для выбора основной. Рабочие настройки и OpenCode оставлены на 8k.

## Полный тест GPU FA со shared memory

Экспериментальная FA-only сборка прошла 50/50 матричных тестов, 9/9 вращений KV и 34/34 тестов внимания. Реальная модель прошла короткий и длинный поиск контрольных строк, повторное использование префикса и API/tool-call проверки. Граф содержит две части.

На документе 9996 токенов: первый запрос 1505,53 с (prefill 1494,78 с), повтор 9,02 с, новый хвост 10,98 с. Генерация в этих запросах 3,56–4,34 токена/с. По сравнению с предыдущим тестом 16k с CPU fallback первый запрос медленнее примерно на 32%, повтор быстрее примерно в 2,43 раза. Это отдельные прогоны, а не контролируемая серия измерений. Ускорение всего повторного запроса относительно первого около 167 раз; 6268,74x в отчёте относится только к использованию кэша на этапе prefill, не к ускорению GPU относительно CPU.

Корректность подтверждена в рамках этих тестов; ускорения первичной обработки нет. Рабочий демон восстановлен на 8k, экспериментальная сборка не установлена как основная. Отчёт: `logs/context16k-gpu-fa-benchmark.json`.
