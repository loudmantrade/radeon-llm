# LLM на Radeon Pro 560X

Локальный эксперимент для Intel MacBook Pro с Radeon Pro 560X 4 ГБ.

## Состав

- Движок: upstream llama.cpp, commit `2280f0fd163b03d4331d49e08460f66502e35854`.
- Модель: Qwen2.5-1.5B-Instruct, Q4_K_M, 1 117 320 736 байт.
- Источник: https://huggingface.co/Qwen/Qwen2.5-1.5B-Instruct-GGUF
- Ревизия модели: `91cad51170dc346986eccefdc2dd33a9da36ead9`.
- Проверенный SHA-256: `6a1a2eb6d15622bf3c96857206351ba97e1af16c30d7a74ee38970e434e9407e`.
- Лицензия модели: Apache 2.0, копия в `models/LICENSE`.

## Запуск

Открой обычный macOS Terminal и выполни:

```bash
cd /path/to/radeon-llm
./run-radeon.command
```

Можно передать свой запрос:

```bash
./run-radeon.command "Напиши короткую функцию Python для вычисления чисел Фибоначчи."
```

Скрипт выбирает устройство с Radeon в названии и запрашивает перенос всех слоёв на GPU. Если Radeon недоступна, скрипт завершает работу. Проверяй в `logs/radeon-run.log` строки `offloaded ... layers` и имя Metal-устройства: один только запуск программы не доказывает ускорение на GPU.

Контекст ограничен 2048 токенами, ответ 160 токенами. Flash Attention отключён для первого теста старой AMD. Этот запуск проверяет совместимость, а не максимальную скорость.

Для контрольного запуска на CPU:

```bash
./run-cpu.command
```

## Обнаруженная настройка графики

При проверке `pmset -g custom` для питания от сети показал `gpuswitch 0` (принудительная встроенная графика). Скрипты не меняют настройки macOS.

Если хочешь временно принудительно включить Radeon при питании от сети, выполни в Terminal:

```bash
sudo pmset -c gpuswitch 1
./run-radeon.command
```

Вернуть обнаруженное исходное значение для питания от сети:

```bash
sudo pmset -c gpuswitch 0
```

Автоматическое переключение вместо принудительного режима:

```bash
sudo pmset -c gpuswitch 2
```

Параметр `-c` относится только к питанию от сети. Пароль вводится непосредственно в Terminal. Настройки NVRAM проект не меняет.

Список устройств, доступных движку:

```bash
./llama.cpp/build/bin/llama-completion --list-devices
```

## Пересборка

```bash
cmake -S llama.cpp -B llama.cpp/build -DCMAKE_BUILD_TYPE=Release \
  -DGGML_METAL=ON -DGGML_METAL_EMBED_LIBRARY=ON \
  -DLLAMA_BUILD_TESTS=OFF -DLLAMA_BUILD_SERVER=OFF
cmake --build llama.cpp/build --config Release -j 6 --target llama-completion llama-bench
```

## Результат проверки 25 октября 2026

- Сборка `llama-completion` и `llama-bench` завершилась успешно.
- SHA-256 модели совпал с метаданными Hugging Face.
- Контрольный запуск на CPU завершился: обработка запроса 65,29 токена/с, генерация 10,60 токена/с (58 шагов). Это единичный короткий прогон, не полноценный бенчмарк.
- Маленькая модель может давать фактически неверные ответы: первый тест подтвердил работоспособность инференса, но не качество ответов.
- После изменения пользователем `gpuswitch` на `2` процесс Codex по-прежнему не видит ни одного устройства Metal. Причина пока не установлена. Запуск на Radeon из этой среды не состоялся; требуется проверка из обычного Terminal.

Скрипты не меняют системные настройки и глобальные пакеты. Модель запускается локально, запросы не отправляются в облако.

## Запуск из Terminal пользователя

Radeon обнаружена как `MTL0`, модель завершила генерацию без ошибки. Однако текущая реализация выполняет существенную часть вычислений на CPU: в отчёте `CPU_REPACK` занимает 596,53 МиБ, модель на MTL0 округляется до 0 МиБ, а граф разбит на 453 части при генерации. Поэтому строка `offloaded 29/29 layers` сама по себе не подтверждает выполнение всей модели на GPU.

Результаты этого прогона:

| Этап | CPU, контрольный прогон | Radeon + CPU, Terminal |
|---|---:|---:|
| Обработка запроса | 65,29 токена/с | 23,67 токена/с |
| Генерация | 10,60 токена/с | 2,63 токена/с |

Генерация в этом режиме примерно в 4 раза медленнее контрольного CPU-прогона. Прогоны выполнялись в разное время и средах; это ориентировочное сравнение. Исходный пользовательский вывод сохранён в `logs/radeon-user-run.txt`.

В исходниках выбранной версии Metal матричное умножение требует `has_simdgroup_reduction`; определение этой возможности ориентировано на семейства Apple7 и Metal3. Это ограничение совместимости стоит проверить для старой Radeon, прежде чем делать вывод о предельной производительности самого оборудования.

## Vulkan через MoltenVK

SDK LunarG 1.3.296.0 установлен локально в `vulkan-sdk/`, только core-компонент; системная установка не выполнялась. Эта версия содержит инструменты для Intel x86_64. Источник: https://sdk.lunarg.com/sdk/download/1.3.296.0/mac/vulkansdk-macos-1.3.296.0.zip

Сборка использует тот же commit llama.cpp и ту же модель, но отдельную папку `llama.cpp/build-vulkan`, с `GGML_VULKAN=ON` и `GGML_METAL=OFF`. На macOS Vulkan обращается к GPU через MoltenVK, который переводит команды в Metal. При этом вычислительные шейдеры и планирование llama.cpp отличаются от нативного Metal-бэкенда.

Запуск из обычного macOS Terminal:

```bash
cd /path/to/radeon-llm
./run-vulkan.command
```

Только список устройств:

```bash
./run-vulkan.command --list-devices
```

Скрипт сам задаёт пути к локальному Vulkan loader и драйверу MoltenVK. Выбирается только Radeon с именем устройства `VulkanN`. Вывод сохраняется в `logs/vulkan-devices.log` и `logs/vulkan-run.log`. Настройки профиля shell и macOS не меняются.

Для сравнения сохраняются тот же запрос, контекст 2048, batch 128, Flash Attention off и жадная генерация до 160 токенов. В отчёте проверяй не только `offloaded ... layers`, но также размер Vulkan-буфера модели, `CPU_REPACK`, число частей графа и `eval time`.

Пересборка:

```bash
./build-vulkan.command
```

Из процесса Codex MoltenVK сообщает `Metal ... is not available on this device`. Это не доказывает отсутствие поддержки Radeon: нативный Metal-бэкенд из той же среды также не видел GPU, тогда как из обычного Terminal Radeon обнаруживалась.

Vulkan-сборка `llama-completion` и `llama-bench` завершилась успешно. Исполняемый файл проверен через `--version`; скрипты прошли `bash -n`. Проверка `run-vulkan.command --list-devices` из Codex корректно завершилась сообщением о недоступности GPU. Производительность Vulkan пока не измерена: нужен запуск из Terminal пользователя.

## Первый Vulkan-прогон из Terminal: некорректный результат

Radeon получила 934,69 МиБ весов; KV-кэш 56 МиБ; граф разбит на 2 части. Вычисления выполнялись с существенной загрузкой GPU. Получено 47,96 токена/с генерации и 11,41 токена/с обработки запроса, однако ответ состоит из бессвязных фрагментов и повторов. Эти показатели нельзя считать скоростью корректного инференса. Исходный вывод: `logs/vulkan-user-run.txt`.

Для следующей проверки подготовлен `run-vulkan-safe.command`: он отключает FP16-арифметику Vulkan, асинхронное выполнение, fusion, оптимизацию графа и fast math MoltenVK. Это диагностическая конфигурация, а не подтверждённое исправление. Тип KV-кэша и квантование весов не меняются. Сначала нужно получить осмысленный ответ, затем возвращать оптимизации по одной. Лог: `logs/vulkan-safe-run.log`.

```bash
./run-vulkan-safe.command
```

Диагностический режим `run-vulkan-safe.command` также дал некорректный ответ (повторы), при 18,82 токена/с. Отключённые оптимизации не устранили проблему. Исходный вывод: `logs/vulkan-safe-user-run.txt`.

Следующая проверка: `./diagnose-vulkan.command`. Выполняет три коротких запуска с одинаковым арифметическим запросом: CPU, Radeon с FP32 KV-кэшем и microbatch=1 (логический batch=128), затем такой же Radeon без MMVQ. Сохраняются остальные ограничения предыдущего диагностического режима. Разделяет проверку пути prefill/кэша и альтернативного матричного ядра; первопричина пока не установлена. Логи: `logs/vulkan-diagnostic-*.log`. Правильный ответ на тестовый вопрос: `4`; совпадение одного теста ещё не доказывает корректность всей модели.

Контрольный CPU-прогон новой диагностики с microbatch=1 и FP32 KV-кэшем проверен: ответ на `2 + 2` равен `4`. Лог: `logs/vulkan-diagnostic-cpu-precheck.log`.

## Сравнение CPU / Vulkan с FP32-кэшем / Vulkan без MMVQ

CPU ответил `4`; оба GPU-варианта дали одинаковый повторяющийся текст. Уменьшение microbatch до 1, FP32 KV-кэш и отключение MMVQ не устранили ошибку. Эти результаты указывают на некорректность выбранного GPU-пути, но не определяют, в каком компоненте находится первопричина. Лог: `logs/vulkan-three-way-user-run.txt`.

Собран штатный `test-backend-ops`. Скрипт `check-vulkan-ops.command` сравнивает небольшие матричные операции Vulkan0 с CPU-эталоном (F32, F16, Q4_K, Q6_K), сохраняя диагностические ограничения. Фильтр предварительно проверен на CPU: 65/65 тестов прошли. GPU-тест нужно выполнить из обычного Terminal. Лог: `logs/vulkan-ops.log`. Это тест арифметической корректности, не бенчмарк LLM.

```bash
./check-vulkan-ops.command
```

## Подтверждённые ошибки операций и обновление MoltenVK

На Radeon штатный тест дал 20/50 поддержанных тестов OK, 30 FAIL; ещё 15 отфильтрованных случаев не поддерживаются. Ошибки есть в F16, Q4_K, Q6_K и части F32 матричных операций. Это воспроизводится без модели, токенизатора и кириллицы. Отчёт: `logs/vulkan-ops-user-run.txt`.

Скачан официальный MoltenVK 1.4.2 для macOS (универсальная библиотека с x86_64) в `moltenvk-1.4.2/`. Release notes содержат исправление `Fix AMD subgroup size (64→32) and disable Intel UHD 630 simdReduction`. В старом тесте Radeon сообщала warp size 64. Это обоснованная гипотеза причины, но исправление ещё нужно подтвердить на GPU.

Источник и описание: https://github.com/KhronosGroup/MoltenVK/releases/tag/v1.4.2

Vulkan-скрипты теперь по умолчанию используют MoltenVK 1.4.2; старая библиотека в SDK сохранена. Путь можно переопределить через `RADEON_VULKAN_ICD`.

```bash
./verify-vulkan-update.command
```

Этот скрипт сначала запускает тесты матричных операций. Только если они завершились успешно, запускает модель с английскими system/user инструкциями. В среде Codex новая библиотека загружается, но GPU всё ещё недоступна. Проверка shell-синтаксиса всех обновлённых скриптов прошла; GPU-корректность пока не подтверждена.

### Исправление загрузки новой библиотеки

Первый повтор с ICD новой версии всё ещё показывал warp size 64 и 20/50 OK. Трассировка `DYLD_PRINT_LIBRARIES=1` в Codex выявила ошибку настройки: `DYLD_LIBRARY_PATH` указывал на SDK и подменял новую библиотеку старой с тем же именем `libMoltenVK.dylib`. Поэтому тот прогон не проверил новую версию.

Во всех Vulkan-скриптах исправлен приоритет путей: папка выбранного драйвера идёт перед SDK. Трассировка подтвердила загрузку библиотеки именно из `moltenvk-1.4.2/.../libMoltenVK.dylib`; лог `logs/vulkan-library-check-fixed.log`. Тест операций теперь печатает фактически загруженную библиотеку из трассировки. Требуется повтор `verify-vulkan-update.command` из Terminal. Первый отчёт сохранён в `logs/vulkan-update-first-user-run.txt`.

## Подтверждённый успешный запуск MoltenVK 1.4.2

После исправления приоритета библиотек пользовательский лог подтвердил фактическую загрузку MoltenVK 1.4.2. Radeon теперь сообщает warp size 32. Все 50 поддержанных матричных тестов прошли; модель ответила `4` на английский вопрос `2 + 2` и завершила генерацию без повторов. Это подтверждает устранение наблюдавшихся ошибок в проверенных случаях. Полный лог: `logs/vulkan-update-verified-user-run.txt`.

Ответ состоял из одного токена, поэтому 2,82 токена/с из этого прогона не являются устойчивым измерением скорости. Пока подтверждён диагностический режим. Следующий тест производительности можно провести обычным `run-vulkan.command` с более длинным запросом; он использует исправленную библиотеку, но возвращает оптимизации, которые нужно проверить на корректность.

## Vulkan с оптимизациями: более длинный русский ответ

Прогон с MoltenVK 1.4.2 и обычным `run-vulkan.command` завершился без прежних бессвязных повторов. Запрос: «Объясни в пяти предложениях, как работает видеопамять.» GPU: обработка 71,02 токена/с, генерация 28,19 токена/с (88 шагов), генерация и обработка суммарно около 3,89 с, память GPU 1069 МиБ.

Для сравнения в Codex выполнен новый CPU-прогон с тем же запросом и параметрами: обработка 82,96 токена/с, генерация 15,10 токена/с (85 шагов), суммарно около 6,30 с. Ускорение генерации в этих одиночных прогонах около 1,87x; среды и время запуска отличаются, ответы не идентичны. Это не строгий повторяемый бенчмарк.

Оба ответа содержат похожую фактическую ошибку: модель путает видеопамять GPU с накопителем видеофайлов/картами памяти. Ошибка качества ответа воспроизведена на CPU, поэтому её нельзя приписывать только GPU. Матрицы в диагностическом режиме проверены, но исчерпывающая проверка всех операций и оптимизаций не проводилась.

Логи: `logs/vulkan-optimized-user-run.txt` и `logs/cpu-vram-comparison.log`.

## Модель Qwen3-4B-Instruct-2507

Подготовлена более крупная модель Qwen3-4B-Instruct-2507 (4 млрд параметров), non-thinking, квантование Q4_K_M от Unsloth. Размер файла 2 497 281 120 байт (около 2,5 ГБ). Размер и SHA-256 проверены по метаданным репозитория. Источник, ревизия и контрольная сумма сохранены в `models/qwen3-source.json`, лицензия Apache-2.0 в `models/Qwen3-LICENSE`.

- Оригинальная модель: https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507
- GGUF: https://huggingface.co/unsloth/Qwen3-4B-Instruct-2507-GGUF
- Ревизия GGUF: `a06e946bb6b655725eafa393f4a9745d460374c9`.
- SHA-256: `3605803b982cb64aead44f6c1b2ae36e3acdb41d8e46c8a94c6533bc4c67e597`.

Запуск на Radeon:

```bash
./run-qwen3.command
```

Свой запрос:

```bash
./run-qwen3.command "Чем оперативная память отличается от SSD?"
```

Скрипт использует исправленный MoltenVK 1.4.2, контекст 2048 и лимит ответа 320 токенов. Ожидается, что модель с таким контекстом поместится в 4 ГБ VRAM; фактическое размещение нужно проверить в GPU-логе. Старый запуск `run-vulkan.command` по умолчанию продолжает использовать Qwen2.5 1.5B для сравнения. Лог новой модели: `logs/qwen3-vulkan-run.log`.

Контрольный запуск Qwen3 на CPU завершился: 6,16 токена/с генерации, 166 шагов. Модель описала VRAM как память видеокарты для текстур, геометрии и других данных GPU, без прежней путаницы с SD-картами. В ответе остаются технические упрощения; один прогон не является полной оценкой качества. Лог: `logs/qwen3-cpu-check.log`. Скорость и размещение на Radeon пока не проверены.

## Qwen3 4B: подтверждённый запуск на Radeon

Пользовательский запуск завершился связным ответом о VRAM без прежней путаницы с SD-картами. На GPU перенесено 37/37 слоёв. Буферы GPU: веса 2375,91 МиБ, KV-кэш 288 МиБ, вычисления 81,19 МиБ; всего около 2745 МиБ. На CPU остаётся mapped-буфер модели 304,28 МиБ. Контекст 2048 сохранён, автоматическая подгонка параметры не меняла.

Генерация: 10,52 токена/с против 6,16 на CPU (примерно 1,71x). Обработка запроса: 8,29 токена/с против 21,15 на CPU. Суммарное время обработки и генерации: 22,88 с против 29,65 с. GPU-ответ 170 шагов, CPU-ответ 166 шагов; прогоны одиночные, в разное время и из разных сред. Скорость первого prefill может включать разовые расходы, устойчивый бенчмарк не проводился. Исходный вывод: `logs/qwen3-vulkan-user-run.txt`.

## Демон и OpenCode

Реализованы OpenAI-совместимый `llama-server`, управление macOS LaunchAgent, авторизация, проверка API и готовая конфигурация OpenCode. Пошаговый запуск и результаты тестирования: [SERVER.md](SERVER.md).

## KV-кэш на диске

Реализовано сохранение последнего контекста между перезапусками. Включение с проверкой на Radeon: `./enable-kv-cache.command`. Обновляются только скрипты и конфигурация; установленная нативная сборка сохраняется. Инструкция и ограничения: [PERSISTENT-KV.md](PERSISTENT-KV.md). Основной контекст остаётся 8k.

## Профиль KV Q8

Подготовлен профиль 8k/Q8_0 для ключей и значений с проверенной FA-only сборкой. Для установки с резервной копией, API-проверками и проверкой восстановления после перезапуска используйте `./enable-q8.command`. [Инструкция и откат](Q8-DAEMON.md). Изменение исходного config.json само по себе ещё не меняет установленный демон.

## Переход с 8k на 16k

Текущая целевая конфигурация проекта — 16384 токена с KV Q8. Установленный демон меняется после `./enable-16k.command`; OpenCode limit и тайм-аут обновляются после проверок. [Инструкция 16k и откат](DAEMON-16K.md).

## Несколько KV-контекстов

Подготовлен индексированный кэш с точным поиском префикса, счётчиками обращений, очисткой и горячими mmap. Включение с проверкой: `./enable-indexed-cache.command`; статус: `./cache-status.command`. [Устройство, лимиты и откат](INDEXED-CACHE.md).

## Проверка готовых механизмов и переноса фрагментов

Изолированный эксперимент: `./test-native-reuse.command`. Сначала штатный RAM cache, затем `n_cache_reuse` с контролями изменения предыстории. [Совместимость, CPU-результаты и ограничения](NATIVE-REUSE.md). Рабочий профиль автоматически восстанавливается.

## Сдвиг по занятому диапазону и сохранение вывода

Изолированная проверка 16k: `./test-shift-active.command`. [Оптимизация и найденный контрпример качества](SHIFT-ACTIVE.md). Полный вывод сохраняется автоматически; достаточно подтвердить окончание в чате. [Где находятся логи](TEST-LOGS.md).

## Пробное включение в рабочем демоне

По запросу пользователя подготовлен opt-in профиль: `./enable-experimental-reuse.command`. Он включает глобальный `--cache-reuse 64`, активный диапазон сдвига и отдельный кэш; сохраняет профиль для отката и проверяет API/restart. [Управление и известное ограничение качества](EXPERIMENTAL-DAEMON.md).

## Мониторинг Radeon

`./monitor-gpu.command` показывает загрузку, VRAM in use/free, температуру и частоты из IORegistry раз в секунду без sudo. Остановка: Ctrl+C. Один снимок: `--once`; запись CSV: `--csv` (по умолчанию logs/gpu-monitor.csv), интервал: `--interval 1`. Показатели относятся ко всей Radeon, включая экран и другие приложения; used+free могут не включать зарезервированную память. Недоступные поля показываются как N/A.
