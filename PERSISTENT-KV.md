# KV-кэш между перезапусками

Включение и проверка на Radeon из обычного Terminal:

```bash
/path/to/radeon-llm/enable-kv-cache.command
```

Команда обновляет только Python-скрипты и конфигурацию установленного демона, сохраняя его нативные библиотеки, драйвер и модель. Основная конфигурация остаётся 8k, без экспериментального GPU FA. Затем диагностический запрос проверяет сохранение, перезапуск процесса и повторное использование более 90% префикса. Проверка использует последний слот для своего документа; после неё можно продолжить работу в OpenCode.

## Поведение

- Через пять секунд простоя после запросов сохраняется последний слот, если в нём не менее 512 токенов. Короткие служебные запросы не заменяют дисковый снимок.
- При запуске сначала загружается модель, затем восстанавливается снимок. `daemon.command start` сообщает готовность после этой попытки.
- Сохраняется один последний контекст. Совпадающий префикс используется автоматически штатным API llama.cpp; OpenCode менять не нужно. Другая история, другой system prompt и перестановка текста ограничивают повторное использование.
- Снимок включает обработанные токены и KV, но не заменяет историю чата в OpenCode. Клиент продолжает передавать сообщения, а сервер переиспользует совпадающую часть.
- Модель, размеры и время изменения нативных библиотек, аргументы запуска входят в отпечаток совместимости. При изменении отпечатка снимок пропускается. Ошибка чтения также приводит к холодному запуску.
- Снимки находятся в `~/Library/Application Support/radeon-llm/cache/kv`. Каталог закрыт правами 0700, файлы 0600. Кэш содержит данные контекста и не зашифрован отдельно. Во время записи могут одновременно существовать старый и новый снимки; размер растёт с заполнением контекста и может достигать порядка гигабайта.
- Сначала записывается новый файл, затем атомарно меняется индекс. При прерывании записи предыдущий снимок остаётся доступен. После успешной записи старые файлы удаляются.
- Сохранение начинается только после наблюдаемого простоя; при поступлении нового запроса в этот момент штатный сервер может поставить сохранение в очередь. Снимок может отставать от последнего ответа, если демон остановлен до очередного сохранения. При аварии во время вычислений используется последний завершённый снимок.
- Это не ускоряет обработку нового текста и не увеличивает контекст. Первый запрос к новой истории по-прежнему требует вычислений.

## Управление

```bash
./daemon.command update-scripts  # обновить скрипты и перезапустить сервис
./check-kv-cache.command        # повторить проверку через реальный перезапуск
./daemon.command logs           # строки KV cache: saved/restored
```

`persistent_kv: false` в `server/config.json` отключает механизм. После изменения запустите `daemon.command update-scripts`. `kv_idle_seconds` задаёт задержку сохранения. Снимки на диске сохраняются при отключении.

Полное `install` также копирует нативную сборку из проекта; для этого обновления используйте `update-scripts`, чтобы сохранить проверенную установленную сборку.

## Выполненная проверка

Изолированный CPU-сервер с контекстом 2048 был остановлен и запущен заново: снимок 799 токенов, 112,4 МиБ, запись 0,37 с. Повторный запрос использовал 797 токенов кэша из 798 входных, пересчитал один; prefill 18,67 с → 0,14 с. Ответ верный до и после перезапуска. Проверены отказ от несовместимого отпечатка и сохранность предыдущего снимка при ошибке новой записи. Отчёт: `logs/kv-persistence-cpu-check.json`. Проверка GPU выполняется командой включения из обычного Terminal.

## Диагностика запуска LaunchAgent

Первое обновление на Radeon завершилось ожиданием готовности без нового запуска в логах и без каталога KV. Причина пока не подтверждена. Управление сервисом дополнено ожиданием снятия старого задания и закрытия его порта после bootout, явным kickstart после bootstrap, ранними строками запуска перед поиском GPU и выводом состояния LaunchAgent при сбое. Повторное применение: `./enable-kv-cache.command`. GPU-проверка сохранения ещё не выполнена.
