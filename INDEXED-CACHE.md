# Индексированный KV-кэш: диск и горячие mmap

Включение с проверкой на Radeon из обычного Terminal:

```bash
/path/to/radeon-llm/enable-indexed-cache.command
```

Установщик сохраняет текущие скрипты, конфигурацию и снимки, затем обновляет только Python-часть. Нативные библиотеки, модель, 16k/Q8 и адрес OpenCode не меняются. Прежний снимок автоматически переносится в индекс и используется при запуске, если совпадает отпечаток модели/сборки/параметров. Старый снимок без записанных входных токенов доступен для восстановления при старте; поиск по префиксу становится доступен для новых снимков.

Публичный API остаётся `http://127.0.0.1:8080/v1`. Перед ним появляется локальный прокси; нативный llama-server слушает `127.0.0.1:8081` с тем же ключом. Клиенты должны использовать публичный API. API-ключи, исходные запросы, параметры выборки и поток SSE передаются без изменения.

## Выбор и сохранение

1. Прокси использует штатные `/apply-template` и `/tokenize` этой же сборки, включая инструменты, кириллицу и специальные токены.
2. Индекс SQLite содержит сжатые токены входа, отпечаток совместимости, файл снимка, размер, число обращений и время последнего использования. Сам KV хранится отдельным бинарным файлом.
3. Для запроса выбирается самый длинный **точно совпадающий префикс токенов**, от 512 токенов. Никакого поиска по смыслу или переноса контекста похожего текста нет. Если активный GPU-контекст уже лучше или равен, он сохраняется активным.
4. Перед переключением сохраняется исходящий контекст, чтобы можно было вернуться к нему. Обычное фоновое сохранение происходит после пяти секунд простоя. Короткие запросы не создают новые снимки.
5. После успешного запроса увеличиваются счётчики повторного использования. Продолжение той же истории заменяет избыточный более короткий префикс, сохраняя накопленный вес обращений. Разные ветки сохраняются отдельно.
6. Запись файла завершается до транзакции индекса; старый снимок остаётся доступен при ошибке новой записи. Незавершённые файлы удаляются при следующем запуске. Некорректный снимок исключается из индекса; вместо него выполняется обычный пересчёт.

В GPU по-прежнему один слот. Прокси последовательно выполняет выбор/восстановление, генерацию и сохранение. Во время долгой генерации health и статус доступны; статус может сообщить `busy`, не ожидая окончания запроса. Прямые изменения слотов через публичный API инвалидируют отслеживаемый активный контекст. Запросы без кэширования, несколько независимых ответов в одном запросе и запросы с LoRA не индексируются.

## Ограничения и очистка

По умолчанию:

| Параметр server/config.json | Значение | Назначение |
|---|---:|---|
| `kv_disk_mib` | 8192 | Лимит индексированных снимков на диске |
| `kv_hot_mib` | 1024 | Бюджет горячих отображений файлов |
| `kv_max_entries` | 16 | Максимум снимков |
| `kv_ttl_days` | 30 | Срок без использования до удаления |
| `kv_min_tokens` | 512 | Минимальный префикс для поиска/сохранения |

При превышении лимитов удаляются записи с наименьшим весом: `(1 + log2(1 + hits)) / (1 + возраст_последнего_использования_в_днях)`. Так частые обращения повышают приоритет, но старые популярные записи постепенно уступают свежим. Активный снимок защищается от удаления. Очень большой снимок, который сам превышает весь дисковый бюджет, не сохраняется.

Лимит диска относится к управляемым снимкам. Текущая временная запись, SQLite/WAL и резервные копии обновлений в backups могут требовать дополнительное место. Резервные копии не удаляются политикой кэша. Бинарные файлы резервируются жёсткими ссылками, когда это возможно; последующее удаление живого снимка не удаляет резервную копию. Метаданные копируются отдельно.

## Что означает горячий слой RAM

Наиболее свежие и часто используемые совместимые снимки отображаются через `mmap`, а их страницы прогреваются чтением. Это файловый кэш RAM: нативное восстановление читает те же страницы через файловый API без второй полной копии Python. Лимит ограничивает сумму горячих отображений; файл, который целиком не помещается в бюджет, остаётся на диске. Для предельного заполнения 16k снимок может превышать 1 ГиБ.

**Физическое удержание страниц не гарантируется:** macOS может вытеснять их при нехватке памяти. Бюджет mmap не является жёстким ограничением всего системного файлового кэша. Это также не набор дополнительных активных слотов в VRAM: перед использованием снимка KV всё равно переносится на GPU. Нативный `--cache-ram` оставлен равным нулю, чтобы не создавать второй независимо управляемый набор больших копий.

## Управление и откат

```bash
./cache-status.command
./check-indexed-cache.command
./enable-indexed-cache.command --rollback
```

Статус показывает дисковый и горячий объём, список снимков, число повторных обращений, совместимость и попадания. SQLite и снимки находятся в `~/Library/Application Support/radeon-llm/cache/kv`; каталог 0700, файлы закрыты от других пользователей. Они содержат данные истории и не зашифрованы отдельно.

После изменения лимитов в исходном `server/config.json` можно повторить `enable-indexed-cache.command`. Для отключения — откат к профилю перед последним обновлением или `indexed_kv: false` с последующим `daemon.command update-scripts`. Не запускайте несколько демонов с одним каталогом: эксклюзивная блокировка намеренно запрещает это.

## Проверки

На реальном CPU-сервере с Q8 и контекстом 2048 проверено A → B → A, затем перезапуск → B. При повторном использовании восстановлены 653 из 654 входных токенов, пересчитан один. Первичные prefill около 15–17 с, повторные около 0,12 с. Потоковые вызовы инструментов, результат инструмента, авторизация и API прошли через прокси. Отчёт: `logs/indexed-cache-cpu-check.json`.

Автоматические тесты покрывают точный префикс и изоляцию моделей, частоту/свежесть/TTL, лимиты диска и mmap, неполную запись, дедупликацию продолжений, миграцию старого снимка, эксклюзивную блокировку, последовательную обработку конкурентных запросов, неизменный SSE/UTF-8, ошибки базы и сохранность старого снимка при сбое. Откат с резервной копией также проверен. Проверка GPU выполняется установщиком: API, A/B/A, перезапуск, B. Она занимает время двух первичных обработок коротких документов, а не полного 10k-теста.

## Проверка готовых механизмов и переноса фрагментов

Изолированный эксперимент: `./test-native-reuse.command`. Сначала штатный RAM cache, затем `n_cache_reuse` с контролями изменения предыстории. [Совместимость, CPU-результаты и ограничения](NATIVE-REUSE.md). Рабочий профиль автоматически восстанавливается.
