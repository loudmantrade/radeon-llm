# Готовые механизмы KV reuse и эксперимент переноса фрагментов

Проверка Radeon из обычного Terminal:

```bash
/path/to/radeon-llm/test-native-reuse.command
```

Скрипт временно останавливает рабочий демон, запускает отдельный сервер на порту 18091, выполняет оба этапа и восстанавливает прежний профиль в finally. Изменений конфигурации демона, OpenCode и его каталога кэша нет. Native runtime, модель и Q8 берутся из установленного профиля. GPU-прогон использует контекст 16384, диагностический CPU-прогон (`--cpu`) — 2048.

## Совместимость готовых решений

Проверено по официальной документации:

| Решение | Возможности | Применимость к Intel Mac + Radeon 560X/MoltenVK |
|---|---|---|
| vLLM automatic prefix caching | Блочное хранение общего префикса | Официальный GPU-путь AMD использует ROCm; macOS GPU-путь предназначен для Apple Silicon. Готового Vulkan/MoltenVK backend в списке нет |
| LMCache | Внешнее хранение KV-фрагментов, перенос между RAM/SSD | В официальном списке коннекторов указаны vLLM и SGLang; готовый коннектор llama.cpp не указан. Самостоятельная установка хранилища не подключит внутренний KV llama.cpp |
| LMCache CacheBlend | Непрефиксные фрагменты с выборочным пересчётом | Нужна интеграция с вычислительным движком на уровне KV/attention; HTTP-прокси нашего демона такой интеграцией не является |
| llama.cpp `--cache-ram` | Готовый RAM-кэш состояний промптов | Доступен в установленной сборке; проверяется первым этапом. Это ещё не постраничный блочный KV-store |
| llama.cpp `n_cache_reuse` / `--cache-reuse` | Поиск совпадающего фрагмента в предыдущем контексте и перенос KV | Доступен в установленной сборке. Проверяется вторым этапом отдельно от рабочего демона; требует проверки ответов при изменении предыстории |

Источники: [vLLM GPU](https://docs.vllm.ai/en/latest/getting_started/installation/gpu/), [vLLM prefix caching](https://docs.vllm.ai/en/latest/design/prefix_caching/), [LMCache integration](https://docs.lmcache.ai/developer_guide/integration.html), [CacheBlend](https://docs.lmcache.ai/kv_cache_optimizations/cacheblend.html), [llama-server](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md).

Подтверждения работающего готового пути LMCache/CacheBlend → llama.cpp → Vulkan/MoltenVK для этой машины не найдено. Эти пакеты не устанавливались в системный Python: без нужного коннектора такая установка не даст переиспользования KV на Radeon. Прототип paged KV в [обсуждении llama.cpp](https://github.com/ggml-org/llama.cpp/discussions/21961) отдельно откладывает prefix caching и сериализацию на следующий этап; его нельзя считать готовой заменой.

## Этап 1: штатный RAM prefix cache

Один сервер с `--cache-ram 512`, перенос фрагментов отключён. Запросы A → B → A проверяют, что движок сам возвращается к сохранённому состоянию A. Все ответы должны быть правильными, повторный A должен использовать более 90% префикса. Это проверка готовой возможности установленного llama.cpp, без нового кода GPU.

## Этап 2: экспериментальный non-prefix reuse

RAM-кэш отключается, чтобы ранее вычисленный полный запрос не маскировал перенос фрагментов. Для каждого случая выполняются:

1. Полный пересчёт нового запроса (`cache_prompt=false`).
2. Прогрев старого запроса без переиспользования.
3. Новый запрос с точным префиксом и `n_cache_reuse=0` — контроль.
4. Повторный чистый прогрев старого запроса.
5. Новый запрос с `n_cache_reuse=64`.

Случаи: удаление нейтрального примечания; удаление OVERRIDE для цвета; удаление OVERRIDE для кода; замена OVERRIDE на новое значение. Во всех случаях длинный оставшийся текст совпадает, но при удалении переопределений и замене значения меняется правильный ответ из-за другой предыстории. Это позволяет отличить реальное сохранение качества от удачного совпадения одинаковых ответов.

В отчёте отдельно сохраняются корректность контролей, ответ после переноса и число дополнительно переиспользованных токенов. Совпавший ответ при нулевом дополнительном reuse не считается подтверждением работы переноса. Даже все пройденные короткие случаи не доказывают сохранение качества на произвольном коде. KV shifting не равен CacheBlend: он не выполняет выборочный пересчёт влияния новой предыстории на все перенесённые состояния.

Отдельные этапы:

```bash
./test-native-reuse.command --phase prefix
./test-native-reuse.command --phase shift
```

Результаты: `logs/native-reuse-gpu.json`, `logs/native-reuse-gpu-prefix.log`, `logs/native-reuse-gpu-shift.log`. CPU-проверка пишет соответствующие файлы с `cpu` в имени.

## Граница текущего эксперимента

Этот тест не добавляет физическую дедупликацию отдельных KV-блоков на диске и не устанавливает LMCache. Он применяет реально доступные готовые функции llama.cpp, затем проверяет экспериментальный перенос непрефиксных фрагментов. Следующий этап для полноценного блочного хранилища — совместимый адаптер экспорта/загрузки диапазонов KV. Для произвольного объединения фрагментов дополнительно нужен выборочный пересчёт и сравнение с полным prefill. Рабочий профиль не переводится на приблизительное reuse по итогам нескольких коротких тестов.

При `--phase prefix` или `--phase shift` JSON-результат сохраняется отдельно с суффиксом `-prefix-results` или `-shift-results`, чтобы не выдавать пропущенный этап за выполненный. Первоначальный CPU-тест с неоднозначными контрольными задачами сохранён в `logs/native-reuse-cpu-initial-controls-invalid.json` и не используется как подтверждение качества.

## Полученные CPU-результаты

Штатный RAM cache: A/B/A прошёл, возврат к A переиспользовал 523 из 524 входных токенов, prefill около 16,53 с → 0,15 с.

После уточнения контрольных инструкций все четыре случая и исходные ответы прошли. При удалении примечания и двух OVERRIDE-строк перенесены фрагменты: дополнительно переиспользованы 145–146 токенов по сравнению с точным префиксом, пересчитан один токен, prefill около 0,30–0,42 с вместо 3,30–3,57 с у точного префиксного контроля. Ответы совпали с полным пересчётом. При замене RED на новое GREEN дополнительного reuse не было: пересчитаны 148 токенов, prefill около 3,21 с, ответ верный.

Это отдельные короткие прогоны CPU, не доказательство сохранения качества на произвольных контекстах и не замер Radeon. CPU-этапы выполнялись отдельно; объединённый отчёт явно содержит `phases_executed_separately`. Новый код дополнительно сохраняет ответы обоих прогревов источника и проверяет каждый. Экспериментальный перенос не включён в установленном демоне.

## Результат Radeon и выявленный регресс

Штатный RAM prefix cache прошёл A/B/A: 10,76 с → 0,15 с prefill. Все четыре контрольные задачи shift корректны, в трёх случаях переносились по 146 токенов. Exact-prefix → shift prefill: нейтральное удаление 3,35 → 3,56 с; удаление override 4,67 → 1,54 с; удаление override кода 4,77 → 1,55 с. Замена значения не дала дополнительного reuse.

После первого shift генерация устойчиво замедлилась примерно с 8 до 1,18 токена/с, включая последующие запросы без shift. При завершении native server сообщил увеличение compute buffer с 23,33 до 256,125 МиБ. Это основание подозревать давление на память или проблему управления вычислительным буфером, но не доказательство конкретной причины. Перенос не включён в рабочем демоне.

Фокусированный контроль размера контекста:

```bash
./test-native-reuse.command --phase shift --context 8192 --case override_removal --probe-decode
```

Этот режим оставляет производственный профиль 16k без изменений, проводит один случай на изолированном 8k сервере и сравнивает генерацию до/после сдвига на одинаковом запросе до 32 токенов. В конце возвращает рабочий демон. Отчёт: `logs/native-reuse-gpu-ctx8192-shift-results.json`. Для парного контроля 16k используется та же команда с `--context 16384`.

Фокусированный тест с измерением генерации проверен на CPU/2048: контрольные ответы и перенос прошли; генерация до/после 7,54 → 7,55 токена/с, устойчивого замедления в этом режиме нет. Это не отделяет влияние backend от размера контекста — для этого нужен подготовленный GPU/8192 прогон. Логи фокусированных запусков получают суффикс случая и `-decode-probe`, чтобы сохранить исходный полный GPU-лог.
