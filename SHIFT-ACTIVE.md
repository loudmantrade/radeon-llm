# Изолированная оптимизация временного буфера K-shift

Проверка на Radeon с контекстом 16k:

```bash
/path/to/radeon-llm/test-shift-active.command
```

Скрипт сохраняет полный консольный вывод автоматически. После окончания достаточно написать в чате «тест завершён»; копировать вывод не нужно. Рабочий демон временно останавливается и восстанавливается в finally. Нативная сборка установленного демона не заменяется.

## Основание

В исходном GPU/16k тесте после первого KV shift compute buffer увеличился с 23,33 до 256,125 МиБ, генерация замедлилась примерно с 8 до 1,18 токена/с. На GPU/8k буфер вырос только до 128,094 МиБ, а генерация до/после сохранилась: 8,35 → 8,31 токена/с. Это согласуется с давлением на память при 16k, но не доказывает конкретный механизм регресса.

Исходный `build_graph_shift` строит dequantize/Hadamard/RoPE/quantize для всей ёмкости KV. При 16k даже запрос около 200 токенов создаёт граф на 16384 ячейки.

## Изменение

В отдельной сборке `experimental/shift-active/bin` добавлен opt-in `LLAMA_KV_SHIFT_ACTIVE_ONLY=1`. При одном потоке KV граф ограничивается диапазоном от нулевой до последней занятой **физической** ячейки. Пустые промежутки внутри этого диапазона учитываются; использовать только число токенов было бы неверно после удаления или перемещения. Таблица сдвигов и view ключей имеют одинаковый укороченный размер. При выключенном opt-in и при нескольких потоках сохраняется полный диапазон.

Основная ёмкость 16k и выделенный KV-буфер Q8 не уменьшаются. Меняется только временный граф сдвига. При заполнении всего контекста выигрыша от укорочения диапазона не будет. Это не полноценный paged KV-store и не реализация CacheBlend.

## Проверено перед GPU-прогоном

- Сборка и проверка diff прошли.
- CPU/2048, исходный контроль: около 7,54 → 7,55 токена/с.
- CPU/2048, новый вариант: около 7,60 → 7,73 токена/с, сдвиг по 205 из 2048 ячеек, ответы короткого теста верны.
- Два отдельных случая с промежутками в физических ячейках: полные сериализованные Q8 KV-состояния, включая checkpoints, **побайтно совпали** между установленной исходной сборкой и новой сборкой. SHA256 записаны в `logs/shift-active-cpu-state-equivalence.json`.

## Отдельно о качестве переноса фрагментов

Расширенный тест обнаружил контрпример ещё в исходном алгоритме KV reuse: при 23 нейтральных строках удаляется `OVERRIDE=RED`, остаётся `DEFAULT=BLUE`. Полный пересчёт отвечает BLUE, старый источник отвечает RED, перенос фрагмента ошибочно отвечает RED. Новая оптимизация даёт такое же KV-состояние и тот же результат, что исходный алгоритм. Это подтверждает сохранение поведения оптимизацией, **но не корректность приблизительного переноса при другой предыстории**.

Контрпример включён в общий эксперимент как `context_sensitive_removal`. Все пять случаев и проба генерации выполняются новой командой. Ошибочный ответ в этом случае — диагностический результат, а не повод включать режим в рабочем демоне. Код выхода 0 у эксперимента означает завершение измерений; качество нужно оценивать по полям `shift_controls_passed`, `shift_answers_passed` и отдельным ответам в JSON.

## Где читать результат

- `logs/latest-native-reuse.json`: команда, состояние, время, код выхода и путь к полному выводу.
- `logs/sessions/`: полный stdout и stderr каждого запуска.
- `logs/native-reuse-gpu-active-shift-shift-results.json`: ответы, скорость генерации до/после, параметры памяти и подтверждение активного диапазона.
- `logs/native-reuse-gpu-active-shift-shift-decode-probe.log`: подробный лог нативного сервера.

Можно выполнить один случай:

```bash
./test-shift-active.command --case override_removal
```

Сборка экспериментальная. Результат на Radeon ещё нужно получить; рабочий профиль сохраняет перенос фрагментов выключенным.

## Первый GPU-прогон новой сборки

В выполненных четырёх случаях compute buffer остался 23,33 МиБ, предупреждения об увеличении до 256 МиБ нет. После переносов генерация оставалась около 8 токенов/с. Prefill переноса: 0,323 с, 0,143 с, 0,142 с; при замене префикса дополнительного reuse нет. Ответы и контроли этих четырёх случаев верны.

Запуск прервался на пятом случае из-за ошибки Python-разбора дополнительных полей (`too many values to unpack`). Демон восстановлен, исходный отчёт сохранён отдельно как `logs/native-reuse-gpu-active-shift-four-cases-before-runner-fix.json`. Ошибка исправлена через общий decode_case с регрессионными тестами стандартного и расширенного форматов. Полная последующая проба генерации в этом запуске не выполнена — её нельзя считать пройденной.

Достаточный повтор для недостающего случая и пробы генерации:

```bash
./test-shift-active.command --case context_sensitive_removal
```

## Заключительный GPU-контроль

Последний фокусированный запуск завершился с кодом 0, демон восстановлен. Для context_sensitive_removal полный и точный префиксный пересчёт дают BLUE; перенос на Radeon тоже дал BLUE. Переиспользовано 269 из 270 токенов, пересчитан один. Prefill точного контроля 4,762 с → 0,167 с; wall 4,893 с → 0,295 с. Проба генерации до/после: 8,348 → 8,327 токена/с. Compute buffer в конце 23 МиБ, сдвиг по 274 физическим ячейкам из 16384.

Вместе с предыдущим частичным запуском проверены пять GPU-случаев, ответы и контроли верны. Это два отдельных запуска, не один полный непрерывный прогон. Оптимизация временного диапазона устранила наблюдавшийся регресс на проверенных коротких запросах. CPU-контрпример качества переноса сохраняется: там тот же чувствительный случай даёт RED. Отсутствие ошибок на пяти GPU-случаях не гарантирует корректность произвольного непрефиксного reuse. В рабочем демоне этот режим по-прежнему выключен. Сводка: `logs/shift-active-gpu-validation.json`.

## Пробное включение в рабочем демоне

По запросу пользователя подготовлен opt-in профиль: `./enable-experimental-reuse.command`. Он включает глобальный `--cache-reuse 64`, активный диапазон сдвига и отдельный кэш; сохраняет профиль для отката и проверяет API/restart. [Управление и известное ограничение качества](EXPERIMENTAL-DAEMON.md).
